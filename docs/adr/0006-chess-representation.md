# Chess representation and rules

The new `Game` plays real 8×8 chess with a **133-action space**: 64 quiet moves + 64 captures (en passant encodes as a capture on its destination square) + 5 castles — the facebookresearch/AlphaZero convention, fixed for every position so generation can batch. (An earlier draft said "189 = 64×{quiet, capture} + 5 castles"; that arithmetic was wrong, 64+64+5 = 133. Promotion piece is selected at execution time, not in the action space; if the model ever makes visibly dumb promotion choices, a later effort can add the 56 promotion slots.) and an **8-plane input** (6 piece-type planes signed by side + castling rights + en-passant target; the halfmove-clock/age planes of the 15-plane convention are omitted). We rejected the 15-plane AlphaZero representation (en-passant, halfmove clock, game age) because the missing information only matters in long drawish games, which a day-scale self-play budget never reaches, while it costs ~2× the representation of the 8-plane choice and multiplies net FLOPs, MCTS leaf-eval, and buffer memory everywhere. Move generation and draw detection (checkmate, stalemate, threefold repetition, insufficient material) are delegated to `python-chess` (already in requirements): a move-generation bug would silently poison self-play data, which is worse than its ~1 ms cost. Games terminate on checkmate/stalemate, on threefold repetition (early cut to avoid weak-model shuffling), insufficient material, or a 150-halfmove hard cap; all draws score 0. Changing the plane count or action encoding later means a from-scratch retrain, so revisit only from a new effort.
